# 意拍 IntentShot PRD v1.0｜对抗性评审（通用视角）

- 评审对象：`/Users/nick/CascadeProjects/intentshot/docs/PRD.md`（v1.0，2026-09-27）
- 参照文档：`/Users/nick/CascadeProjects/intentshot/docs/ARCHITECTURE.md`、`/Users/nick/CascadeProjects/intentshot/docs/UI-UX.md`
- 评审立场：对抗性。目标是在这份文档驱动 UX、架构与 epics 规划之前，找出会让下游返工的假设、矛盾与不可验收项。

---

## 总体裁决

这份 PRD 作为愿景陈述是干净、克制、诚实的（它反复强调"不作保证""不预设门槛"），但正因如此，它作为**决策文档是不合格的**：它把最响亮的承诺（"说出你想拍的，剩下的交给意拍"）建立在自己明确声明不可控的能力之上；把全部可判定性（性能门槛、指标目标值、稳定性参数）推迟到一个既没有定义、也没有退出判据的"真机 Spike"之后；把 32 条 FR 与 11 条 MVP 纳入项之间的映射责任甩给读者；甚至把一条自家 UX 文档承认可能物理不可实现的指令（"背景再暗一点"）写成了主流程的旗舰示例。7 大节所有指标没有任何测量定义、分母、数据来源或目标值，10 大节验收标准全部是流程性检查而非结果性检查——照现在的验收，背景完全没有虚化的成片也能让 MVP"通过验收"。下游 epics 阶段在第一批 story 就会撞上这些问题：性能故事写不出验收、实时调整的交互模式（自动应用还是仅建议）无据可依、作品页整页 UI 无 FR 支撑、JEV 三个字母无人能解释。建议在进入架构/epics 之前完成一轮修订，重点是 C 级三项。

---

## Findings

### C-01｜价值主张与公开 API 能力边界正面冲突：最核心的承诺效果（背景虚化、色调、景深）恰好是公开 API 最不可控的部分

- **严重度：** critical
- **位置：** 1.1 / 1.3 / 1.4 / 2.2，对照 NFR-08、FR-08、FR-31
- **攻击：** 1.1 承诺"自动生成并应用拍摄方案，帮助用户更容易拍出接近预期的照片"，1.3 承诺"说出你想拍的，剩下的交给意拍"，2.2 把"背景虚化"列为人像场景第一诉求。但 1.4 自己划了边界："系统只使用公开、可用的 API 和设备运行时能力；无法控制的成像算法或硬件能力不作保证。"问题在于这两段话不能同时成立：AVFoundation 公开 API 中镜头光圈是只读的固定硬件值，人像背景虚化依赖系统人像模式的计算摄影链路，第三方无法在拍摄时控制虚化强度；夜景模式（Night mode）同样不对三方开放；"电影感/暖调"只剩白平衡增益在 min/max 区间内的有限调节。也就是说，产品价值主张里最有说服力的那几个效果，全部落在自己声明的"不作保证"区域里。FR-08"通过公开相机 API 应用设备支持的参数"与 FR-31"不支持的目标应降级或说明"意味着：用户说"背景虚化"，系统最可能的兑现方式是一句说明 + 焦距/曝光补偿的微调。这不是免责声明能盖住的问题——这是 MVP 的核心场景可能空转的问题。
- **建议修复：** 在 PRD 增加一张"承诺效果 × 公开 API 手段 × 可控程度"对照表（作为附录或新 FR），逐项标注背景虚化、脸部明亮、暖调、景深、夜景各自的可实现路径与降级形态；据此裁剪 2.2 场景列表与第 10 节验收；把"哪些效果做不到"从免责条款升级为明确的产品决策（哪些承诺保留、哪些改口、哪些砍掉）。

### C-02｜目标设备与最低系统版本从未定义：产品在"无本地模型设备"上的形态是二义的

- **严重度：** critical
- **位置：** 全文；8.1 技术 Spike；6.1；FR-05/FR-19/FR-20
- **攻击：** PRD 通篇只说"本地模型"，从未出现 Foundation Models、最低 iOS 版本或目标机型集合。8.1 要"验证目标设备的本地模型可用性"，但"目标设备"这四个字本身就没定义。这不是细节遗漏，而是产品定义的分叉口：若最低版本锁定为支持 Apple Intelligence 的机型，可服务设备存量极小，App Store 上架后大多数用户根本装不上或装上不可用；若不设限，那么对绝大多数用户而言，FR-19 的降级链路（"退化到预设方案、规则引擎或基础相机能力"）就是**默认体验**——产品实际形态是一个带摄影文案的模板相机应用，"AI 智能相机"的定位对这部分用户是虚假宣传。PRD 对此只字未提。另外，PRD 的核心技术赌注（Apple Foundation Models 的设备门控）从未在 PRD 层面命名，只读 PRD 的人（比如老板、投资人、UX）根本不知道整个产品押在一个系统级可用性开关上。
- **建议修复：** 在 PRD 明确（哪怕以"Spike 待定参数"形式）最低 iOS 版本与目标机型集合；写明不满足条件的设备是"不支持安装"还是"降级可用"，若降级可用则必须为该形态单独定义目标用户与验收；在 1.1 或 8.1 点名核心技术依赖及其设备门控条件。

### C-03｜全文档零数值门槛，且所有可判定性被推迟到一个没有退出判据的 Spike 之后

- **严重度：** critical
- **位置：** 5 NFR-02/NFR-05；7 目标设定原则；8 发布与验证计划；9 风险表
- **攻击：** NFR-02 写"自然语言解析和方案生成需达到可接受的交互响应；具体 P50/P95 目标在真机基准测试后确定"——"可接受的"由谁接受？这是自我引用，不是标准。第 7 节干脆宣布"当前不预设未经真机和用户测试支持的数值门槛。先建立基线，再确定可验证的目标值"。于是这份 PRD 里**没有任何一个可判定通过/失败的量化标准**。更糟的是，承担解锁全部数值的第 8 节 Spike 本身没有通过/失败判据、没有时限、没有"失败后怎么办"——风险表第一行"本地模型在目标设备上的能力/可用性未确认"的应对只有"运行时检查，先做真机 Spike"。如果 Spike 的结论是"本地模型解析质量不够"，PRD 没有计划 B：没有云端解析备选、没有缩小 MVP 的预案、没有任何决策规则。下游 epics 的性能故事和验收标准将全部写成"待真机后确定"，这在 sprint 层面等于没有验收。
- **建议修复：** 为 Spike 定义明确的 go/no-go 判据与时限（例如：本地解析 P95 ≤ X 秒、Schema 合规率 ≥ Y% 的**临时门槛**，标注可修订）；给 NFR-02/NFR-05 设临时量级（交互响应秒级、实时分析帧率/毫秒级）；增加"Spike 失败决策树"（缩 MVP / 引入云端解析 / 暂停立项）；给第 8 节每个阶段补退出条件。

### H-04｜主流程旗舰示例是产品自己承认可能做不到的指令，且把"参数调整"与"构图引导"混为一谈

- **严重度：** high
- **位置：** 3.1 步骤 9；FR-12；FR-02；对照 UI-UX 3.8
- **攻击：** 3.1 步骤 9 写'用户可以说"背景再暗一点"或"人物往中间一些"，系统生成局部调整方案。'第一条指令，恰好是 UI-UX 3.8 自己承认的物理难题："若硬件无法独立控制主体与背景亮度，应说明限制并给出替代建议"——公开 API 下主体亮度与背景亮度本来就不是两个可独立控制的旋钮，PRD 的旗舰示例第一句就在演示一个大概率要"说明限制"的场景。第二条更根本："人物往中间一些"根本不是相机参数——机器动不了人，它只能给出构图引导（辅助线/语音提示）或裁切建议。而 FR-12 只笼统地说"只修改相关目标，并尽量保留其他已确认目标"，FR-02 的意图 Schema（主体、风格、目标、优先级、约束、不确定项）里甚至没有构图字段。参数类调整、模式类调整、构图引导类调整三类完全不同的输出物在 PRD 里被揉成一个"局部调整方案"，epic 拆分时会当场爆炸。
- **建议修复：** 在 PRD 建立调整对象类型学（参数类 / 模式类 / 构图引导类），FR-12 明确每类的输出物与验收差异；主流程示例换成当前 API 边界内可兑现的指令（如"脸部亮一点、整体偏暖"），或显式标注示例中哪些走引导路径。

### H-05｜验收标准只验流程不验结果，且与 MVP 纳入清单、FR 体系不对齐

- **严重度：** high
- **位置：** 10 验收标准（MVP）；对照 6.1、FR-14/15/16/17/23/24/27/28/32
- **攻击：** 验收写"人像基础场景可以生成、预览并应用拍摄方案"——"应用"成功只说明参数写进去了，不说明照片达到了用户描述的效果。按这 8 条验收，一张背景毫无虚化、脸照样死黑的照片，只要 FR-07 的"部分应用"提示弹了出来，MVP 就算通过。这是典型的"考勤式验收"。同时，MVP 纳入清单里的"少量预设方案与方案复用"没有任何验收条目；FR-16 手动覆盖、FR-17 用户偏好、FR-23 撤销、FR-24 无障碍、FR-27/28 引导与帮助、FR-32 一键拍摄全部不在验收清单内——它们是 MVP 的一部分还是不是？验收环节拒绝回答。
- **建议修复：** 验收改为结果导向：为"应用方案"补充效果断言（在 N 台测试机上，人像场景成片的人脸亮度、主体清晰度达到预先定义的可判定分级）；逐条核对 6.1 纳入项，要么补验收，要么显式声明"不在 MVP 验收范围（P1）"。

### H-06｜核心指标几乎全部没有测量定义，部分指标没有任何 FR 支撑，"匿名"与"留存"互相矛盾

- **严重度：** high
- **位置：** 7 核心指标；FR-25/FR-26；9 风险表
- **攻击：** 逐条拷问："用户主动反馈的'比原生相机更省事'比例"——FR-25 只提供"满意/不满意 + 标注主要问题"，全 PRD 没有任何 FR 定义过这道对比问题，这个指标永远测不出来。"意图解析准确率"——准确是相对什么金标准？需要人工标注的测试语料，而"回归测试集"只出现在风险表的缓解栏里，没有任何 FR 或计划为构建/标注语料出资出人。"拍摄任务完成率"——"任务"从未被定义。"首次拍摄满意度"——统计单位是第一张照片还是首次会话？FR-25 没说。还有更基础的矛盾：FR-25 承诺"经授权的匿名统计数据"、FR-26 承诺避免过度采集，但"7/30 日留存"必须依赖跨会话持久标识符——匿名与留存统计在口径上不可兼得，PRD 两边都想要。反向看，FR-09 构图辅助、FR-13 稳定性、FR-17 偏好、FR-21 状态管理、FR-23 撤销、FR-24 无障碍、FR-27/28、FR-32 没有任何指标会去验证它们——它们死了也没人知道。
- **建议修复：** 为每个保留指标写三件事：测量定义（事件、分母、统计窗口）、数据来源（哪个 FR/埋点）、决策用途（多少算成功、失败后改什么）；补一个 FR 承载"比原生相机更省事"的问法或砍掉该指标；为意图解析建标注集立项（规模与标注规则至少给数量级）；明确标识方案（授权后的伪匿名 ID），解决留存与匿名的口径冲突。

### H-07｜实时取景调整到底是"自动应用"还是"仅建议"：FR-29、FR-13 与体验原则三方打架

- **严重度：** high
- **位置：** FR-29 / FR-13 / FR-16；3.2 关键体验原则；对照 UI-UX 3.6
- **攻击：** FR-29 说系统"生成有限、可解释的调整建议"——建议，听起来不自动应用。但 FR-13 的存在前提是"避免自动参数反复来回变化"——说明参数会被自动应用，否则防什么抖动？3.2 体验原则"自动调整要可感知、可撤销，避免参数无提示地跳动"再次确认存在自动应用。而 FR-16 又说用户手动覆盖后"系统应尊重用户设置"。于是最核心的拍摄中交互模式——场景变化时系统是直接拧参数，还是弹一个建议让用户点——在 PRD 里没有答案。这直接决定取景器的整个交互设计、FR-13 防抖的作用对象、FR-23 撤销的语义，是 UX 与 epic 阶段绕不开的第一个决定，PRD 却把它留成了 含糊。
- **建议修复：** 在 PRD 明确默认模式（仅建议 / 自动应用+一键撤销 / 混合并可在设置切换），写清自动应用的作用参数范围与 FR-16 锁定的优先级关系，并给 FR-29 补验收（如"非锁定参数自动调整必须有对应撤销入口"）。

### H-08｜品牌口号承诺语音，MVP 只有打字：承诺与首版体验直接背离

- **严重度：** high
- **位置：** 1.3 核心价值主张；FR-01；3.1 主流程
- **攻击：** 1.3 的口号是"说出你想拍的，剩下的交给意拍"，FR-27 引导还要"通过示例帮助用户理解自然语言拍摄"。但 FR-01 白纸黑字："用户可通过文本输入描述拍摄目标；后续可评估语音输入。"也就是说 MVP 里用户不是"说"，是**打字**——在单手举着手机、户外阳光下、竖屏取景的状态下，用中文键盘输入"拍一张人物清晰、背景虚化、脸部明亮的电影感人像"这么长的句子。这是全流程最大的摩擦点，而品牌每天在向用户承诺相反的东西。第一代用户会按口号形成预期，然后被输入法劝退，留存指标（讽刺的是它自己还测不了）会替你完成这次证伪。
- **建议修复：** 三选一并写进 PRD：(a) 把最小语音输入（按住说话→转文本）纳入 MVP；(b) 口号降级为"写下你想拍的"或改成不承诺输入方式的表述；(c) 在 FR-01 明确 MVP 仅文本，并要求引导文案与商店截图不得暗示语音能力。

### H-09｜JEV 全文从未定义，却进入了暂缓清单、指标体系与验证计划

- **严重度：** high
- **位置：** 6.2 / 6.3 / 7 技术指标 / 8.4 / 9 风险表
- **攻击：** 6.2 暂缓清单写着"JEV 成为必需依赖的正式功能"，第 7 节要测"云端 JEV 调用延迟、失败率与单次成本（仅实验组）"，8.4 有"JEV 对照实验"。但整份 PRD（架构文档同样）**从未展开 JEV 是什么**——是某个厂商产品？某类模型？内部代号？一份决策文档围绕一个未定义的三字缩写做出了暂缓决定、埋了指标、排了实验。更荒诞的是 6.2 那句本身：暂缓一个"成为必需依赖"的状态，等于给一个不存在的东西办暂缓手续，明显是早期草案把 JEV 当核心依赖、后来降级成实验时留下的残迹，没清干净。读 PRD 的人只能靠猜，而架构文档里它又叫 "JEV Decision Adapter"——两份文档一起看仍然不知道它指什么。
- **建议修复：** 在首次出现处给出 JEV 的定义、候选实现类别与选型状态；重写 6.2 该条为正向表述（如"任何外部决策服务不得成为基础拍摄链路的必需依赖"）；或把 6.3/8.4 整体移入附录实验计划。

### H-10｜UI-UX 设计了"作品"一级导航，PRD 没有任何 FR 支撑它；视频口径两份文档不一致

- **严重度：** high
- **位置：** 跨文档：PRD 第 4 节 / 6.1；UI-UX 2、3.10、3.9
- **攻击：** UI-UX 第 2 节要求"底部主导航建议控制在三个入口"，第三个就是"作品：照片/视频作品浏览与方案关联"，3.10 还设计了照片网格、时间分组、方案关联。而 PRD 第 4 节 32 条 FR 里没有任何一条覆盖应用内作品页——FR-10 只管"拍照、预览、重拍、保存和进入系统照片库"。同时 PRD 2.2 明确视频"首期不作为核心承诺"，UI-UX 的作品页却写"照片/视频作品浏览"。UI-UX 3.9 方案库分类里还有"夜景（按版本开放）"——"按版本"是哪个版本？PRD 6.2 明确暂缓"复杂夜景自动摄影"。这三处合并说明：UX 文档已经画出了一个比 PRD 范围更大的产品，epic 规划如果照 UI-UX 拆，会无中生有一整页功能；如果照 PRD 拆，会砍掉一个已设计好的一级导航。
- **建议修复：** PRD 要么补"作品页（最小版：本地照片网格 + 方案关联）"的 FR 并纳入 6.1，要么在 UI-UX 显式标注作品页/视频入口为非 MVP；统一视频与夜景在两份文档中的口径。

### M-11｜MVP 边界自相矛盾："人像场景优先" vs 预设示例"暖调美食" vs 2.2 四大场景

- **严重度：** medium
- **位置：** 6.1；FR-15；2.2
- **攻击：** 6.1 纳入项写"人像场景优先"，但 FR-15 的预设示例是"'自然人像''电影感人像''暖调美食'等"——"等"字前面塞进了一个非人像场景。问题不是挑刺：暖调美食预设要做对，需要食物场景识别与色调策略，而 6.1 的感知范围只有"Vision 人脸/主体基础分析"，美食根本不在感知覆盖内；一个没有场景感知兜底的"暖调美食"预设就是一份硬编码白平衡偏移，正是 FR-15 自己警告的"预设不应冒充保证成片效果"。同时 2.2 把美食/静物、旅行风景、夜景全列为"核心场景"，与 6.1 的"人像优先"之间没有任何过渡说明——这四个场景是 MVP 全做、MVP 只做人像、还是 2.2 只是想表达"产品终将覆盖"？三种读法对应三倍的工作量差距。
- **建议修复：** 给出 MVP 预设白名单（建议 3 个人像变体），把"暖调美食"等移入 6.2 暂缓；在 2.2 显式标注各场景的版本归属（MVP / P1 / 暂缓）。

### M-12｜FR-03 澄清与折中之间没有决策规则，"或"字给了实现方永久逃逸口

- **严重度：** medium
- **位置：** FR-03；对照 UI-UX 4 状态表
- **攻击：** FR-03："系统应提出澄清问题**或**生成折中策略。"一个"或"字意味着实现可以永远只做折中、永不澄清，也永远算合规——而 UI-UX 已经为"需要澄清"设计了"单一问题卡片"状态。什么时候问、什么时候自己拍板折中，是这个产品体验里最体现"智能"含量的决策点，PRD 完全放空。结果可以预见：工程实现会选择简单的那条路（永远折中、永不提问），用户对着一份自己没点过头的方案一头雾水，"复杂或互相冲突的需求应解释限制"（3.2）沦为摆设。
- **建议修复：** 定义澄清触发规则（例：目标间存在硬冲突、且意图对象中用户优先级缺失/矛盾时澄清，否则折中并解释），并给 FR-03 补可测验收（如"对标注冲突的测试用例集，系统触发澄清或折中的正确率与解释完整性"）。

### M-13｜只能撤销一次的"历史"是装饰：FR-23 与迭代闭环、3.1 主流程冲突

- **严重度：** medium
- **位置：** FR-23；FR-30；FR-16；3.1 步骤 9-10
- **攻击：** FR-23 标题叫"方案版本与调整历史"，正文却只承诺"支持撤销最近一次 AI 调整"。一次。而 3.1 主流程鼓励连续多轮调整（步骤 9 说'背景再暗一点'或'人物往中间一些'，步骤 10 还要保存复用），FR-30 又定义了多轮迭代流程。两轮调整走偏之后，用户无路可退——上一版方案在"历史"里看得见摸不着。FR-16 的"允许恢复 AI 方案"恢复的也是当前方案而不是历史版本。记录了版本却不给回退能力，那这个"历史"除了埋点还有什么用？
- **建议修复：** 明确撤销深度（建议至少 N 步栈式撤销，或完整版本树回退），写清 FR-23 的版本列表、FR-16 的"恢复 AI 方案"与撤销栈三者的关系和优先级。

### M-14｜FR-11 评估器自身的正确性无校准计划，"景深效果""构图"的可量化性存疑，风险应对循环论证

- **严重度：** medium
- **位置：** FR-11；9 风险表"审美难以客观量化"行
- **攻击：** FR-11 要"对主体清晰度、曝光、构图、景深效果等可量化指标进行分析"。其中"景深效果"从单张 RGB 成片（无深度数据时）根本谈不上量化，"构图"的达成与否没有客观 ground truth。更重要的是元问题：FR-11 输出的 achieved/partial/not-achieved 判断本身准不准，谁说了算？PRD 没有任何校准计划。风险表的应对是"分场景目标指标 + 用户反馈"——这是循环论证：用户反馈用来校准评估器，而评估器生成的调整建议又在塑造用户反馈；评估器错了，调整建议就错，用户越调越偏，满意度数据反而"证实"评估器没问题。整个反馈闭环建立在一个未被验证的评估器上。
- **建议修复：** 把 FR-11 首版指标收窄为算法定义明确的项（人脸亮度、主体清晰度、有深度数据时的虚化代理指标），每项标注数据来源与已知局限；安排小规模人工标注校准（评估结论 vs 人工判断的一致率），作为 8.3 可用性测试的一部分。

### M-15｜"不得导致持续抖动"没有测度，防抖参数全部未定，且 Spike 不覆盖稳定性调参

- **严重度：** medium
- **位置：** NFR-03；FR-13；8.1 Spike
- **攻击：** NFR-03"参数更新不得导致持续抖动"——抖动定义是什么？每秒几次算抖？方向交替算不算？没有测度的 NFR 无法验收，只能靠评审人主观点头。FR-13 的阈值、冷却时间、滞回机制全部无数值，这本身可以接受（要真机调），但 8.1 的 Spike 清单是"本地模型可用性、相机 API 控制边界、Vision 能力与功耗"——稳定性调参不在其中，原型阶段（8.2）也没提。风险表把"自动调整干扰用户"的应对押在"用户锁定、撤销、冷却机制"上，等于用一个未验证的机制去缓解一个未定义的问题。
- **建议修复：** 给抖动下可测定义（例：60 秒窗口内同一参数的自动变更 ≤ N 次、且不出现方向交替震荡）；把防抖参数调优显式列入 8.2 原型验证范围，并给 FR-13 一个可在真机上复现的震荡测试用例集。

### M-16｜目标市场、合规与上架要求整体缺席

- **严重度：** medium
- **位置：** 全文；FR-01；FR-25/FR-26；9 风险表"用户价值不足以支撑付费"行
- **攻击：** FR-01"支持中文常见摄影表达"暗示首发中文市场，但 PRD 对是哪个市场（中国大陆 / 港台 / 海外中文用户）只字未提，这直接决定输入法形态、商店、审核与合规要求（隐私政策、账号/数据删除、AI 相关声明、中国大陆区的备案要求等），也决定"经授权的匿名统计"（FR-25）的授权机制怎么做。风险表里出现"用户价值不足以支撑付费"，说明商业模式在决策射程内，但全文没有任何商业假设（免费？订阅？买断？）——"付费意愿"要验证的东西连假设都没写下来。
- **建议修复：** 在 PRD 增加目标市场与合规清单小节（哪怕一页），写明首发地区、上架渠道、需要提前启动的合规事项；用一句话写下当前商业假设及其验证方式，挂接到 8.3/8.5。

### L-17｜FR-32 "简单方案"无定义

- **严重度：** low
- **位置：** FR-32
- **攻击：** "对于用户已确认的简单方案，支持快速应用"——"简单"由谁判定、按什么判据？参数维度数？目标冲突数？历史成功应用次数？不定 义就没法测，epic 只能自由发挥。
- **建议修复：** 给出判据（例：单一策略、无冲突目标、且该方案已成功应用过至少一次），或改为"用户标记为常用的一键方案"这种用户侧可判定的口径。

### L-18｜无量词泛滥："少量""必要""有限""按需"遍布关键 FR，验收无锚点

- **严重度：** low
- **位置：** FR-04"按需触发"；FR-09"必要的构图辅助"；FR-15"少量可理解的场景方案"；FR-29"有限、可解释的调整建议"
- **攻击：** 这些词在 PRD 里不是过渡性措辞，而是需求的实际边界——"少量"预设是 3 个还是 30 个，"按需"的触发条件是什么，"有限"建议的上限是几条，全部决定了工作量和 UI 密度，全部没有答案。UX 和 epic 阶段只能替 PRD 做这些决定，然后 PRD 失去对成品的约束力。
- **建议修复：** 每处给数量级或定义触发/上限规则（允许标注"初值待原型确定"，但要有初值）；至少 FR-15 给出 MVP 预设数量，FR-29 给出单次建议条数上限与触发条件。
