# PRD Quality Review — 意拍 IntentShot PRD v1.0

评审对象：`/Users/nick/CascadeProjects/intentshot/docs/PRD.md`（v1.0，产品定义 / MVP 规划）
评审依据：`prd-validation-checklist.md` 七维度质量标尺。
背景校准：该 PRD 为链顶文档——下游已存在 `docs/UI-UX.md` 与 `docs/ARCHITECTURE.md`，且两份文档明显由本 PRD 派生（UI-UX 复述"取景器是主界面"、"可撤销、可手动接管"；ARCHITECTURE 复述"本地优先"）。因此第 6、7 维度按链顶消费级产品标准从严。

## Overall verdict

这份 PRD 最站得住的是它的诚实边界：§1.4 产品边界主动声明"不承诺完全控制 iOS 原生相机的所有能力"，§7 明确"当前不预设未经真机和用户测试支持的数值门槛"，§8 用 Spike→原型→可用性测试的阶梯而非直接承诺，这些让它作为方向决策文档可信。风险在于两点：一是下游可用性明显弱于链顶文档所需——无 Glossary、关键范围决策所依赖的 "JEV" 全文从未定义、用户旅程只有一条无主角的线性主流程；二是若干场景级取舍（美食/旅行/夜景是否在 MVP 内）与 FR-12 与验收标准之间的口径差被静默处理。进 UX/架构拆解前需要补名词表、JEV 定义与 FR↔验收追溯，否则下游只能靠猜。

## Decision-readiness — adequate

决策以决策的形态出现，不是"考虑事项"。§1.4 用四条边界定义了不做什么；§6.2 暂缓清单里"JEV 成为必需依赖的正式功能"是一条真实的取舍；§7 目标设定原则把数值门槛的推迟本身作为一个明示决策（"先建立基线，再确定可验证的目标值"），并解释了理由。§9 风险表收录了"用户价值不足以支撑付费"这类不利假设，应对是"原型阶段验证频率、留存与付费意愿"——即商业模式问题被推到原型之后，这是明确的排序决策而非回避。

但有张力被抹平了。§2.2 把"美食/静物""旅行与风景""夜景"都列为核心场景，而 §6.1 MVP 纳入只写"人像场景优先"，§6.2 暂缓只写"复杂夜景自动摄影"——美食、旅行、简单夜景三者到底在不在 MVP 内没有答案，而 FR-15 又把"暖调美食"列为预设方案，暗示美食部分在。一个读到 §2.2 的决策者会以为产品首期覆盖五个场景，读到 §6.1 才发现是一个半。此外全文没有 Open Questions 区、没有任何 `[NOTE FOR PM]` 式标记——真实存在的不确定项（本地模型能力"未确认"、付费意愿）全部以"风险已应对"的口吻写进 §9，读者无法分辨哪些未确认项会 gate 绿灯、哪些只是执行细节。

### Findings
- **medium** 关键场景的 MVP 取舍未言明 (§2.2 vs §6.1/6.2) — "美食/静物""旅行与风景""夜景"列为核心场景，MVP 纳入仅"人像场景优先"，暂缓仅覆盖"复杂夜景自动摄影"；FR-15 的"暖调美食"预设又部分 contradict。*Fix:* 在 §6 明确逐场景纳入/部分纳入/暂缓，并把 FR-15 与场景决策对齐。
- **medium** 未确认前提以已应对口吻呈现 (§9, §8) — "本地模型在目标设备上的能力/可用性未确认"是本 PRD 最大的技术赌注，但它只出现在风险表；没有 Open Questions 区标注该项是否阻塞 MVP 启动、Spike 失败时回退到哪个范围。*Fix:* 增加 Open Questions 区，为 Spike 失败情形写明降级范围决策。
- **low** FR-12 与验收标准口径不一致 (FR-12 vs §10) — FR-12 说"尽量保留其他已确认目标"，§10 验收写"系统保留未修改的目标"，验收比需求更硬，"尽量"未被解释。*Fix:* 统一为可判定口径（例如"除用户指定修改项外其余目标字段值不变"）。

## Substance over theater — strong

几乎没有家具。三个画像（§2.1）数量克制且各自驱动了真实需求：内容创作者的"保存和复用方案"落在 FR-14/FR-15，轻度爱好者的"不想每次从头调参"落在方案复用与 FR-32。NFR 不是模板货：NFR-01"相机核心链路不得依赖云端模型"、NFR-07"避免把模型置信度包装成成片成功保证"、NFR-08"白名单、范围、能力和状态校验"都是只属于这款产品、且可检验的表述。愿景（§1.2）虽然品类通用，但 §1.3 的价值主张"说出你想拍的，剩下的交给意拍"与闭环表述（"意图理解—场景分析—相机配置—实际拍摄—效果反馈"）有 FR 全链路支撑，不属创新剧场。FR-24/26/27/28 属 iOS 应用标配，但各自带产品化内容（如 FR-27 "说明产品能力边界、相机权限和本地处理原则"），不算凑数。

仅两处偏弱：FR-32 与 FR-07 的区别边界含糊；§2.2 把"视频"列为场景又立即声明"首期不作为核心承诺"，这一条对读者没有信息量。

### Findings
- **low** FR-32 与 FR-07 边界含糊 (FR-32, FR-07) — FR-07 是"查看方案摘要后应用"，FR-32 是"对于用户已确认的简单方案，支持快速应用"，"已确认""简单方案"均未定义，两 FR 可能拆出重复故事。*Fix:* 明确一键模式跳过的是哪一步、进入条件是什么。
- **low** "视频"占位场景 (§2.2) — 列为核心场景同句即声明"后续版本探索，首期不作为核心承诺"，属装点性列举。*Fix:* 移入 §6.2 暂缓，§2.2 只留首期场景。

## Strategic coherence — strong

PRD 有明确论点：自然语言意图到相机执行的闭环能替代参数知识（§1.3、§2.3 JTBD"让我更少试错地获得满意照片"）。功能排序服从论点：FR-01 至 FR-13 全部服务闭环本体，FR-14 至 FR-17 服务复用与留存，FR-18 至 FR-28 是平台卫生，且 §6.1 用"人像场景优先"给出收缩逻辑。成功指标验证论点而非活跃度："从描述需求到完成拍摄的耗时""平均重拍/调整次数""拍摄任务完成率""比原生相机更省事比例"都是闭环有效性的直接度量，不是 DAU/MAU 式活动量。MVP 类型是问题解决型，范围逻辑一致。

两处缺口：其一，论点的可证伪行为没有被度量——产品赌的是"用户愿意把相机配置交给 AI"，但 FR-09 允许关闭辅助、FR-16 允许手动覆盖，指标体系（§7）却没有"辅助关闭率""手动覆盖后回流 AI 的比率"这类反指标；若大量用户拿了方案就关掉 AI，论点已败但现有指标看不出来。其二，所有数值目标后置（§7 目标设定原则），诚实但没有把测定时点绑定到 §8 计划节点，导致指标区在绿灯时不可判伪。

### Findings
- **medium** 缺少反指标 (§7 vs FR-09/FR-16) — 辅助关闭、手动覆盖后不再回流是论点被证伪的直接信号，指标体系未覆盖。*Fix:* 增加如"AI 方案应用后 7 日内仍启用辅助的会话占比"。
- **low** 数值目标后置未绑定决策时点 (§7) — "先建立基线，再确定可验证的目标值"未写明由 §8 哪一步产出、何时回填。*Fix:* 标注目标值回填的触发节点（如小规模可用性测试后）。

## Done-ness clarity — adequate

多数 FR 带有可检验后果：FR-02 "输出必须通过 Schema 校验"、FR-07 要求区分"应用成功、部分应用或无法应用的项目"三种显示态、FR-05 "不得将某一机型的能力写死为所有设备通用"、FR-08 的校验清单、FR-22 逐项列举错误场景。§10 验收标准八条覆盖闭环主干，给出 MVP 级"done"的粗粒度定义，这是本维度最重要的加分项。

弱集中在核心差异化环节。FR-11 是闭环的落点——"对主体清晰度、曝光、构图、景深效果等可量化指标进行分析，并结合原始意图评估目标达成情况"——但意图属性如何映射到可测图像指标（"脸部明亮"对应什么测量与阈值）、"目标达成"以什么形态呈现给用户（§3.1 步骤 8 只说"展示照片及目标达成反馈"）都没有答案，而 §10 验收里也没有对应条目。FR-29 整条由限定词构成（"按需评估""偏离""有限、可解释的调整建议"），无触发条件、无数量边界。NFR-02 "可接受的交互响应"是有意后置但连测定时点都未挂接。另外 FR-30 与 FR-11/FR-12 的分工（拍摄前调整 vs 拍摄后迭代）在文本上难以划清，拆故事时易重复。

### Findings
- **high** FR-11 "目标达成"评估语义未定义 (FR-11, §3.1 步骤8) — 意图属性到可测量图像指标的映射规则、达成度的计算与呈现形态均缺失；这是产品闭环的核心环节，下游架构与故事创作无法从这里起步。*Fix:* 为每类意图属性定义度量方式与判定阈值来源，并写明反馈 UI 呈现的最小信息集。
- **medium** FR-29 全限定词无边界 (FR-29) — "按需""有限""可解释"三个词都没有可判定条件。*Fix:* 定义评估触发时机（如方案应用后、构图显著变化时）与建议条数上限。
- **medium** NFR-02 阈值后置且无测定时点 (NFR-02) — "具体 P50/P95 目标在真机基准测试后确定"，但未绑定 §8 的 Spike 节点，也没有解析/生成各环节的分解口径。*Fix:* 挂接到 §8 步骤 1，并列出需分别测定的环节。
- **low** FR-13 无防抖量化口径 (FR-13) — 机制列举到位（"阈值、冷却时间、滞回机制"），但"避免自动参数反复来回变化"缺可检验上限（如单位时间自动调整次数）。*Fix:* 补一个暂定上限并标注待真机校准。
- **low** FR-24 "足够对比度"无标准 (FR-24) — 可引用 WCAG 数值。*Fix:* 标注对比度比值下限。
- **low** FR-30 与 FR-11/FR-12 分工模糊 (FR-30) — "拍摄后将图像分析结果与用户意图对照"与 FR-11 的分析、FR-12 的调整存在重叠。*Fix:* 写明 FR-30 独有的状态转换（进入"评估后迭代"会话态）。

## Scope honesty — adequate

去范围化总体是显式的、做了实事：§1.4 四条边界、§6.2 六条暂缓（含"JEV 成为必需依赖的正式功能"这种具体取舍）、§6.3 把 JEV 圈定为"仅作为可选对照实验"。§8 的阶梯式验证计划本身就是诚实的 de-scoping——商业模式留到第 5 步。

缺口在标记体系与静默去范围。全文没有一个 `[ASSUMPTION]` 或 `[NOTE FOR PM]` 标记，也没有索引；"iOS（首发）"隐含的跨平台前提、默认中文输入（FR-01 "系统应支持中文常见摄影表达"隐含语言范围）、云端决策服务是否存在于 MVP（FR-18 写"若调用"，ARCHITECTURE 已写"JEV 为可选决策增强服务"）都是未标注的推断。更实质的是场景静默去范围：§2.2 与 §6 之间的美食/旅行/夜景取舍没有出现在任何暂缓清单里（此问题在 Decision-readiness 已记，此处指其范围属性）。开放项密度按标尺衡量：这是一份尚未绿灯、自带验证阶梯的 PRD，无标记高密度反而可接受，但当前是"真实不确定性高、标记密度为零"，读者靠 §9 才能拼出不确定性全貌。

### Findings
- **medium** 场景级去范围未显式化 (§2.2 vs §6.2) — 美食（仅存于 FR-15 预设）、旅行/风景（完全无 FR 覆盖）的 MVP 状态需读者自行推断。*Fix:* 并入 §6.2 或新增"部分纳入"小节。
- **medium** 零假设标记、零开放项标记 (全文) — 隐含前提（跨平台、语言范围、云端服务是否在 MVP）未以 `[ASSUMPTION]` 形式显式化并索引。*Fix:* 补假设标记与索引，至少覆盖上述三项。
- **low** JEV 实验无退出准则 (§6.3) — "比较加入 JEV 前后的实际收益"未定义收益口径与采纳/放弃的判定条件。*Fix:* 写明实验的成功阈值与两条出路。

## Downstream usability — thin

这是与链顶身份差距最大的一维。无 Glossary；FR-01 至 FR-32、NFR-01 至 NFR-08 编号连续唯一（这点干净），但全文没有任何按 ID 的交叉引用——§6.1 MVP 纳入清单、§10 验收标准八条全部用散文复述需求，无法反向定位到 FR。各节单独抽出基本可读（§3.2 体验原则尤其自足），但核心名词在字段义与通用义之间漂移：FR-02 把"目标"定义为意图对象的子字段（"主体、风格、目标、优先级、约束"），而 FR-11/FR-12/§10 中"目标"又指用户整体意图（"结合原始意图评估目标达成情况""保留未修改的目标"）。

最重的问题是 JEV。它在 §6.2（暂缓"JEV 成为必需依赖的正式功能"）、§6.3、§7（"云端 JEV 调用延迟、失败率与单次成本"）、§8（"JEV 对照实验"）、§9 五处出现，承载了一条暂缓决策、一项实验、一组成本指标，但全文从未展开这个词，也没有 Glossary 兜底——下游（含已存在的 ARCHITECTURE.md，其头部的"JEV 为可选决策增强服务"即依赖此定义）只能各自猜。

用户旅程侧：§3.1 是一条无具名主角的线性十步主流程。对消费级产品，冲突需求（FR-03）、降级（FR-19）、手动覆盖（FR-16）、中断恢复（FR-21）这些高价值旅程全部只以 FR 散文存在，没有对应旅程。UI-UX.md 已经在自行补这些设计判断，说明下游在替代而非引用 PRD。

### Findings
- **critical** "JEV" 全文未定义 (§6.2, §6.3, §7, §8, §9) — 一个承载暂缓决策、实验设计与成本指标的术语从未展开，无 Glossary；下游架构文档已在自行定义（"JEV 为可选决策增强服务"），两文档定义来源断裂。*Fix:* 首次出现处展开全称并建立 Glossary 词条，注明其与本地模型/规则引擎的关系。
- **high** 无 Glossary 且核心名词语义漂移 (FR-02 vs FR-11/FR-12/§10) — "目标"在意图对象字段义与用户意图整体义之间摇摆；"意图/拍摄意图/结构化意图/摄影意图对象"变体并存。*Fix:* 建 Glossary，固定"意图（Intent）"为对象、"目标（Objective）"为字段，全文替换统一。
- **medium** 无具名主角的情景旅程 (§3.1) — 消费级链顶产品仅有单一线性主流程，冲突、降级、覆盖、中断四类旅程无 UJ 承载。*Fix:* 补 2–3 条具名主角旅程（如冲突需求、模型降级），主角从 §2.1 三个画像取。
- **medium** §6.1 与 §10 无 FR 引用 (§6.1, §10) — 验收八条与 MVP 纳入清单均为散文，无法追溯覆盖了哪些 FR、遗漏了哪些（如 FR-24 无障碍未出现在任何验收条目）。*Fix:* 为每条验收与纳入项标注 FR ID。
- **low** 版本信息不全 (文档头) — 有"版本 v1.0 / 状态"无日期与作者，多文档并行时无法对齐版本。*Fix:* 补日期与作者字段。

## Shape fit — adequate

形状与产品基本匹配：消费级 iOS 产品、有 §3 体验章节、验收区、发布计划，未过度形式化（32 条 FR 对相机应用不算冗余，且 §6.1 给出收缩）。§3.2 关键体验原则是全文质量最高的段落之一——"用户始终可以拍摄，不被 AI 流程锁死""用户明确锁定的参数和目标，不应被系统随意覆盖"是能直接约束 UX 与架构的产品判断。两处形状问题：一是如上，旅程形式化低于消费级链顶所需（已在 Downstream usability 记录，不重复计数）；二是 JEV 研究议程与产品 PRD 混装——§6.3、§7 实验组指标、§8 第 4 步、§9 风险四处构成一条研究支线，虽被"仅作为可选对照实验"圈住，但把实验词汇带进了产品决策文档并贡献了本文最严重的未定义术语。

### Findings
- **low** 研究议程与产品 PRD 混装 (§6.3, §7, §8, §9) — JEV 对照实验属探索性研究而非 MVP 需求，占四节篇幅并引入未定义术语。*Fix:* 收敛为一处（§6.3），其余位置仅引用。
