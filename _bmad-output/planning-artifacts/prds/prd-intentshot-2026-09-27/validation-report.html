Adversarial review（对抗性评审）

_bmad-output/planning-artifacts/prds/prd-intentshot-2026-09-27/review-adversarial-general.md

这份 PRD 作为愿景陈述是干净、克制、诚实的，但正因如此，它作为决策文档是不合格的：它把最响亮的承诺（"说出你想拍的，剩下的交给意拍"）建立在自己明确声明不可控的能力之上；把全部可判定性推迟到一个既没有定义、也没有退出判据的"真机 Spike"之后；把 32 条 FR 与 11 条 MVP 纳入项之间的映射责任甩给读者；甚至把一条自家 UX 文档承认可能物理不可实现的指令（"背景再暗一点"）写成了主流程的旗舰示例。第 7 节所有指标没有任何测量定义、分母、数据来源或目标值，第 10 节验收标准全部是流程性检查而非结果性检查——照现在的验收，背景完全没有虚化的成片也能让 MVP"通过验收"。下游 epics 阶段在第一批 story 就会撞上这些问题。建议在进入架构/epics 之前完成一轮修订，重点是 C 级三项。

critical

C-01 价值主张与公开 API 能力边界正面冲突：最核心的承诺效果恰好是公开 API 最不可控的部分

1.1 / 1.3 / 1.4 / 2.2，对照 NFR-08、FR-08、FR-31
1.1 承诺"自动生成并应用拍摄方案，帮助用户更容易拍出接近预期的照片"，2.2 把"背景虚化"列为人像场景第一诉求。但 AVFoundation 公开 API 中镜头光圈是只读的固定硬件值，人像背景虚化依赖系统人像模式的计算摄影链路，第三方无法在拍摄时控制虚化强度；夜景模式同样不对三方开放；"电影感/暖调"只剩白平衡增益的有限调节。产品价值主张里最有说服力的那几个效果，全部落在自己声明的"不作保证"区域里。这不是免责声明能盖住的问题——这是 MVP 的核心场景可能空转的问题。
Fix: 增加"承诺效果 × 公开 API 手段 × 可控程度"对照表，逐项标注可实现路径与降级形态；据此裁剪 2.2 场景列表与第 10 节验收；把"哪些效果做不到"从免责条款升级为明确的产品决策。
critical

C-02 目标设备与最低系统版本从未定义：产品在"无本地模型设备"上的形态是二义的

全文；8.1 技术 Spike；6.1；FR-05/FR-19/FR-20
PRD 通篇只说"本地模型"，从未出现 Foundation Models、最低 iOS 版本或目标机型集合。若最低版本锁定为支持 Apple Intelligence 的机型，可服务设备存量极小；若不设限，FR-19 的降级链路就是默认体验——产品实际形态是一个带摄影文案的模板相机应用，"AI 智能相机"的定位对这部分用户是虚假宣传。PRD 的核心技术赌注从未在 PRD 层面命名。
Fix: 明确（哪怕以"Spike 待定参数"形式）最低 iOS 版本与目标机型集合；写明不满足条件的设备是"不支持安装"还是"降级可用"；在 1.1 或 8.1 点名核心技术依赖及其设备门控条件。
critical

C-03 全文档零数值门槛，且所有可判定性被推迟到一个没有退出判据的 Spike 之后

5 NFR-02/NFR-05；7 目标设定原则；8 发布与验证计划；9 风险表
NFR-02"可接受的交互响应"是自我引用，不是标准。这份 PRD 里没有任何一个可判定通过/失败的量化标准。更糟的是，承担解锁全部数值的 Spike 本身没有通过/失败判据、没有时限、没有"失败后怎么办"——如果 Spike 的结论是"本地模型解析质量不够"，PRD 没有计划 B。下游 epics 的性能故事和验收标准将全部写成"待真机后确定"，在 sprint 层面等于没有验收。
Fix: 为 Spike 定义明确的 go/no-go 判据与时限（临时门槛，标注可修订）；给 NFR-02/NFR-05 设临时量级；增加"Spike 失败决策树"（缩 MVP / 引入云端解析 / 暂停立项）；给第 8 节每个阶段补退出条件。
high

H-04 主流程旗舰示例是产品自己承认可能做不到的指令，且把"参数调整"与"构图引导"混为一谈

3.1 步骤 9；FR-12；FR-02；对照 UI-UX 3.8
"背景再暗一点"恰好是 UI-UX 3.8 自己承认的物理难题——公开 API 下主体亮度与背景亮度本来就不是两个可独立控制的旋钮；"人物往中间一些"根本不是相机参数——机器动不了人，只能给出构图引导或裁切建议。而 FR-02 的意图 Schema 里甚至没有构图字段。参数类调整、模式类调整、构图引导类调整三类完全不同的输出物在 PRD 里被揉成一个"局部调整方案"，epic 拆分时会当场爆炸。
Fix: 建立调整对象类型学（参数类 / 模式类 / 构图引导类），FR-12 明确每类的输出物与验收差异；主流程示例换成当前 API 边界内可兑现的指令。
high

H-05 验收标准只验流程不验结果，且与 MVP 纳入清单、FR 体系不对齐

10 验收标准；对照 6.1、FR-14/15/16/17/23/24/27/28/32
验收写"人像基础场景可以生成、预览并应用拍摄方案"——"应用"成功只说明参数写进去了，不说明照片达到了用户描述的效果。按这 8 条验收，一张背景毫无虚化、脸照样死黑的照片，只要"部分应用"提示弹了出来，MVP 就算通过。FR-16/17/23/24/27/28/32 全部不在验收清单内——它们是 MVP 的一部分还是不是？验收环节拒绝回答。
Fix: 验收改为结果导向（在 N 台测试机上，人像场景成片的人脸亮度、主体清晰度达到预先定义的可判定分级）；逐条核对 6.1 纳入项，要么补验收，要么显式声明不在 MVP 验收范围。
high

H-06 核心指标几乎全部没有测量定义，部分指标没有任何 FR 支撑，"匿名"与"留存"互相矛盾

7 核心指标；FR-25/FR-26；9 风险表
"比原生相机更省事比例"没有任何 FR 定义过这道对比问题，永远测不出来；"意图解析准确率"没有金标准语料；"拍摄任务完成率"的"任务"从未被定义；FR-25 承诺"匿名统计"但"7/30 日留存"必须依赖跨会话持久标识符——两边都想要，口径不可兼得。反向看，FR-09/13/17/21/23/24/27/28/32 没有任何指标会去验证它们——它们死了也没人知道。
Fix: 为每个保留指标写测量定义、数据来源、决策用途；补一个 FR 承载"比原生相机更省事"的问法或砍掉该指标；为意图解析建标注集立项；明确标识方案（授权后的伪匿名 ID）。
high

H-07 实时取景调整到底是"自动应用"还是"仅建议"：FR-29、FR-13 与体验原则三方打架

FR-29 / FR-13 / FR-16；3.2 关键体验原则；对照 UI-UX 3.6
FR-29 说系统"生成有限、可解释的调整建议"——听起来不自动应用。但 FR-13 的存在前提是"避免自动参数反复来回变化"——说明参数会被自动应用。3.2 体验原则再次确认存在自动应用。最核心的拍摄中交互模式——场景变化时系统是直接拧参数，还是弹一个建议让用户点——在 PRD 里没有答案。这直接决定取景器的整个交互设计、FR-13 防抖的作用对象、FR-23 撤销的语义。
Fix: 明确默认模式（仅建议 / 自动应用+一键撤销 / 混合并可切换），写清自动应用的作用参数范围与 FR-16 锁定的优先级关系，并给 FR-29 补验收。
high

H-08 品牌口号承诺语音，MVP 只有打字：承诺与首版体验直接背离

1.3 核心价值主张；FR-01；3.1 主流程
1.3 的口号是"说出你想拍的"，但 FR-01 白纸黑字："用户可通过文本输入描述拍摄目标；后续可评估语音输入。"MVP 里用户不是"说"，是打字——在单手举着手机、户外阳光下、竖屏取景的状态下，用中文键盘输入一个长句。这是全流程最大的摩擦点，而品牌每天在向用户承诺相反的东西。
Fix: 三选一并写进 PRD：(a) 把最小语音输入纳入 MVP；(b) 口号降级为"写下你想拍的"；(c) FR-01 明确 MVP 仅文本，并要求引导文案与商店截图不得暗示语音能力。
high

H-09 JEV 全文从未定义，却进入了暂缓清单、指标体系与验证计划

6.2 / 6.3 / 7 技术指标 / 8.4 / 9 风险表
整份 PRD 从未展开 JEV 是什么——是某个厂商产品？某类模型？内部代号？一份决策文档围绕一个未定义的三字缩写做出了暂缓决定、埋了指标、排了实验。6.2 那句"暂缓 JEV 成为必需依赖的正式功能"等于给一个不存在的东西办暂缓手续，明显是早期草案的残迹。
Fix: 首次出现处给出 JEV 的定义、候选实现类别与选型状态；重写 6.2 该条为正向表述；或把 6.3/8.4 整体移入附录实验计划。
high

H-10 UI-UX 设计了"作品"一级导航，PRD 没有任何 FR 支撑它；视频口径两份文档不一致

跨文档：PRD 第 4 节 / 6.1；UI-UX 2、3.10、3.9
UI-UX 第 2 节的第三个主导航入口"作品：照片/视频作品浏览与方案关联"，在 PRD 32 条 FR 里没有任何一条覆盖。PRD 2.2 明确视频"首期不作为核心承诺"，UI-UX 的作品页却写"照片/视频作品浏览"。UX 文档已经画出了一个比 PRD 范围更大的产品——epic 规划照 UI-UX 拆会无中生有一整页功能，照 PRD 拆会砍掉一个已设计好的一级导航。
Fix: PRD 要么补"作品页（最小版）"的 FR 并纳入 6.1，要么在 UI-UX 显式标注作品页/视频入口为非 MVP；统一视频与夜景在两份文档中的口径。
medium

M-11 MVP 边界自相矛盾："人像场景优先" vs 预设示例"暖调美食" vs 2.2 四大场景

6.1；FR-15；2.2
FR-15 的预设示例塞进了非人像场景"暖调美食"，而美食不在 6.1 的感知覆盖内；一个没有场景感知兜底的"暖调美食"预设就是硬编码白平衡偏移。2.2 与 6.1 之间的三种读法对应三倍的工作量差距。
Fix: 给出 MVP 预设白名单（建议 3 个人像变体），把"暖调美食"等移入 6.2 暂缓；在 2.2 显式标注各场景的版本归属。
medium

M-12 FR-03 澄清与折中之间没有决策规则，"或"字给了实现方永久逃逸口

FR-03；对照 UI-UX 4 状态表
"系统应提出澄清问题或生成折中策略"——一个"或"字意味着实现可以永远只做折中、永不澄清，也永远算合规。什么时候问、什么时候自己拍板折中，是这个产品体验里最体现"智能"含量的决策点，PRD 完全放空。
Fix: 定义澄清触发规则（例：目标间存在硬冲突、且用户优先级缺失/矛盾时澄清，否则折中并解释），并给 FR-03 补可测验收。
medium

M-13 只能撤销一次的"历史"是装饰：FR-23 与迭代闭环、3.1 主流程冲突

FR-23；FR-30；FR-16；3.1 步骤 9-10
FR-23 标题叫"方案版本与调整历史"，正文却只承诺"支持撤销最近一次 AI 调整"。两轮调整走偏之后，用户无路可退——上一版方案在"历史"里看得见摸不着。记录了版本却不给回退能力，这个"历史"除了埋点还有什么用？
Fix: 明确撤销深度（建议至少 N 步栈式撤销，或完整版本树回退），写清 FR-23 版本列表、FR-16"恢复 AI 方案"与撤销栈三者的关系。
medium

M-14 FR-11 评估器自身的正确性无校准计划，"景深效果""构图"的可量化性存疑，风险应对循环论证

FR-11；9 风险表"审美难以客观量化"行
"景深效果"从单张 RGB 成片根本谈不上量化，"构图"的达成与否没有客观 ground truth。更重要的元问题：FR-11 输出的判断本身准不准，谁说了算？风险表的应对是循环论证——用户反馈用来校准评估器，评估器生成的调整建议又在塑造用户反馈。整个反馈闭环建立在一个未被验证的评估器上。
Fix: 把 FR-11 首版指标收窄为算法定义明确的项，每项标注数据来源与已知局限；安排小规模人工标注校准，作为 8.3 可用性测试的一部分。
medium

M-15 "不得导致持续抖动"没有测度，防抖参数全部未定，且 Spike 不覆盖稳定性调参

NFR-03；FR-13；8.1 Spike
抖动定义是什么？每秒几次算抖？没有测度的 NFR 无法验收。8.1 的 Spike 清单不含稳定性调参，原型阶段也没提——用一个未验证的机制去缓解一个未定义的问题。
Fix: 给抖动下可测定义（例：60 秒窗口内同一参数的自动变更 ≤ N 次且不出现方向交替震荡）；把防抖参数调优显式列入 8.2 原型验证范围。
medium

M-16 目标市场、合规与上架要求整体缺席

全文；FR-01；FR-25/FR-26；9 风险表
FR-01"支持中文常见摄影表达"暗示首发中文市场，但 PRD 对是哪个市场只字未提——这直接决定输入法形态、商店、审核与合规要求（隐私政策、数据删除、AI 相关声明、备案要求等）。风险表出现"用户价值不足以支撑付费"，但全文没有任何商业假设——"付费意愿"要验证的东西连假设都没写下来。
Fix: 增加目标市场与合规清单小节，写明首发地区、上架渠道、需要提前启动的合规事项；用一句话写下当前商业假设及其验证方式。
low

L-17 FR-32 "简单方案"无定义

FR-32
"简单"由谁判定、按什么判据？参数维度数？目标冲突数？不定义就没法测，epic 只能自由发挥。
Fix: 给出判据（例：单一策略、无冲突目标、且已成功应用过至少一次），或改为"用户标记为常用的一键方案"这种用户侧可判定的口径。
low

L-18 无量词泛滥："少量""必要""有限""按需"遍布关键 FR，验收无锚点

FR-04；FR-09；FR-15；FR-29
这些词是需求的实际边界——"少量"预设是 3 个还是 30 个，"按需"的触发条件是什么，"有限"建议的上限是几条，全部决定工作量和 UI 密度，全部没有答案。UX 和 epic 阶段只能替 PRD 做这些决定，然后 PRD 失去对成品的约束力。
Fix: 每处给数量级或定义触发/上限规则（允许标注"初值待原型确定"，但要有初值）。
